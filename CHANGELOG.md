# Changelog

All entries describe what was genuinely verified in this environment, not aspirational claims. See `README.md`'s "Honesty note" for the full history of what was previously fabricated and removed.

## Unreleased — real Accessibility-tree (AXUIElement) element locator + vision cross-check

**Gap identified:** the previous entry below explicitly noted "There is no Set-of-Marks / Accessibility-API element enumeration in this iteration (considered, not implemented)." Vision-based grounding (`GroundingAgent`) has no independent way to know when `moondream` hallucinates a plausible-but-wrong element - the false-positive case documented below (a "search bar" that didn't exist, agreed on across both coarse and fine stages) is exactly the failure a non-vision cross-check can catch.

**Research first (real GitHub projects, not the big named competitors already covered):** [`axcli`](https://github.com/andelf/axcli) (Playwright-style CLI over AXUIElement with CSS-like selectors), [`AXorcist`](https://github.com/steipete/AXorcist) (Swift chainable/fuzzy AXUIElement queries), [`macos-accessibility-client`](https://github.com/drewster99/macos-accessibility-client) (SwiftUI AX-tree inspector/live-observer), [`pyax`](https://github.com/eeejay/pyax) (Pythonic AXUIElement/AXObserver wrapper). All four are real, working tools confirming the same fact: AXUIElement positions are authoritative OS data, and this is genuinely the mechanism behind "Set-of-Marks"-style grounding on macOS - not something the vision model itself does.

**Feasibility confirmed by direct testing, not assumed:** `osascript` calls to `System Events` (already the project's only automation mechanism, no new dependency) can enumerate real named elements with real positions - `tell process "TextEdit" to get menu bar items of menu bar 1` returned all 8 real menu items with correct names and logical-point positions; `buttons of window 1` returned the 3 real titlebar controls (name empty, but `description` gave the real localized label, e.g. "pulsante di chiusura" for the close button). A real limitation was also found: Finder's toolbar `buttons of window 1` returned real, correct positions but no name/description/title for any button at all - some apps just don't expose a label via System Events. Both outcomes are documented honestly in the module header and README rather than only reporting the win.

**What was built - `src/ax_inspector.ts` (`AXInspector`):**
- `enumerate(processName?)`: real AppleScript query returning every real menu-bar item + window button/radio button/checkbox for a process (defaults to the real frontmost process via `System Events` if omitted), each with real `{role, label, x, y, width, height}` already in the same logical-point "click space" `MouseKeyboardDriver.clickAt` expects - no scale-factor conversion needed, unlike the vision-pixel path in `grounding_agent.ts`. Falls back from `name` to `description` to `title` for the label, matching what was measured working on TextEdit's window controls.
- `crossCheckPoint(clickPoint, keywords, processName?, radiusPx?)`: scans the real element list for one within `radiusPx` of the point and/or with a label matching a keyword, and reports `confirmed`/`matchedElement`/`distancePx` honestly - `false` with a real reason when nothing corroborates, never a fabricated match.
- Wired into `server.ts`: `POST /api/pilot/locate` and `POST /api/pilot/click-by-description` now also run a real `axCrossCheck` after vision grounding succeeds and return it alongside (never used to silently upgrade) `confidence`. New standalone endpoint `GET /api/pilot/ax-elements?process=<name>` returns the raw real element list with no vision/screenshot involved at all.

**How it was verified - real server, real `curl`, real running apps:**
1. Started the actual `bun server.ts` process and called `GET /api/pilot/ax-elements?process=TextEdit` through it - got back all 11 real elements (8 menu bar items + 3 titlebar buttons) matching what direct `osascript` testing had already shown, with correct real coordinates.
2. **Real bug found and fixed during testing, not before:** the first version silently returned `available:true` with 0 elements for a nonexistent process (`?process=NoSuchAppXYZ`), because the AX property lookup errors were being swallowed by an inner `try` block placed too deep in the AppleScript. Fixed by adding an explicit `if not (exists process "...") then error "PROCESS_NOT_FOUND"` check before querying; re-tested and confirmed it now correctly returns `available:false` with an honest "process is not running" reason.
3. `crossCheckPoint({x:183,y:79}, ["close","chiusura"], "TextEdit")` correctly returned `confirmed:true` against the real close-button element (`"pulsante di chiusura"`, center (191,87)), 11.3px away - a genuine independent corroboration of a real coordinate, not a fabricated result.
4. Ran the full `POST /api/pilot/locate` pipeline against real TextEdit with the new `axCrossCheck` wiring live (2x2 coarse/fine grid, 4 real `moondream` queries, ~16.5s) to confirm the integration doesn't crash when vision grounding returns `"not_found"` - `axCrossCheck` correctly stayed `null` in that case (it only runs when a vision coordinate was actually found), consistent with the code path.

**What is still explicitly NOT claimed:** this is not a full AX-tree crawl - it queries menu bar + window buttons/radio buttons/checkboxes only, not arbitrary nested containers (outlines, tables, scroll areas), because `entire contents` was measured to be slow on deep trees and this covers the actual class of element grounding is asked to find. Some apps (measured: Finder's toolbar) expose real positions with no label at all, so `axCrossCheck` for those degrades to weaker positional-only corroboration, or `confirmed:false` if no unlabeled element happens to be close enough either. This is corroboration for the vision path, not a replacement for it - `axCrossCheck` is additive, `confidence` from `GroundingAgent` is unchanged by it.

## Unreleased — real crop-and-reask click-grounding refinement

**Gap identified:** the README stated "No model-driven visual grounding" — the coordinate for every click always had to come from a human or API caller, never from the model looking at the screen and deciding where to click. This is the single most-requested capability in the computer-use-agent space (Anthropic Claude Computer Use, ByteDance UI-TARS, OpenAI Operator, self-operating-computer all center on it), and it's also where this project's own honest self-assessment was weakest: a single local `moondream` model has no dedicated point/bbox head exposed through Ollama's plain `/api/generate`.

**Research first (see README "Grounding research" section for detail):** looked at how the real systems above improve click-grounding beyond one raw coordinate guess - UI-TARS's Set-of-Marks-style element labeling, published "zoom-in click-out" / region-search techniques (crop a candidate region, re-query at higher effective resolution), and Anthropic's own published finding that grid-overlay and quadrant-splitting prompting do NOT reliably help Claude, while a genuine re-crop/zoom does.

**What was built — `src/grounding_agent.ts` (`GroundingAgent`):**
- A real two-stage coarse-grid-then-crop-and-reask search: the real screenshot is split into an NxM grid, each cell is cropped to a real temp PNG (`python3` + Pillow, same mechanism as the existing pixel-diff verification), and each crop is sent to `moondream` with an **open-ended** description prompt. The single matching cell is then subdivided into a finer grid, each sub-cell is cropped **and upscaled**, and re-queried the same way. The center of the smallest matching cell, translated back through both real crop offsets, is the answer.
- Two real, reproducible model behaviors discovered during hands-on testing shaped this design and are documented in the module header: (1) asking `moondream` for raw coordinates over the full screenshot returns a plausible-looking but non-grounded answer (a bounding box covering ~76% of the image for a ~50x25px menu icon); (2) any **closed-form** prompt ("answer only yes or no", "reply with one of: ...") reliably returns an **empty string** from this model via Ollama (`eval_count: 1`, immediate EOS) - so every prompt in the module is open-ended and matching is done by keyword-searching the model's real free-text response.
- A real, previously-unnoticed **2x coordinate-space bug** was found and fixed: `screencapture` on this machine writes PNGs at native Retina pixel resolution (measured 3360x2100) while System Events' `click at {x,y}` operates in logical points (measured 1680x1050 via the same AppleScript call `/api/status` already used). `GroundingAgent.toClickSpace()` now converts explicitly using the real, live-queried scale factor. The pre-existing manual click-through-screenshot feature (`public/app.js`) had this exact bug — every click dispatched that way was landing at up to 2x the intended screen position on this Retina Mac — and has been fixed alongside it (`fetchScreenScaleFactor()` + the corrected `realX`/`realY` conversion in `setupCanvasClickToRealClick`).
- Honest, non-fabricated confidence: `"high"` only when exactly one coarse cell AND exactly one fine sub-cell inside it matched; `"low"` when the stages disagreed or a fallback was needed; `"not_found"` when no cell at either stage ever matched — no coordinate is returned in that case.
- New endpoints: `POST /api/pilot/locate {targetDescription, keywords?}` (grounding only, no click dispatch) and `POST /api/pilot/click-by-description {targetDescription, keywords?, process?, double?}` (grounds, then passes through the existing `SafetyGuard`, then dispatches a real click via `MouseKeyboardDriver.clickAt` at the converted click-space coordinate — refuses with `404` on `"not_found"` rather than clicking a guess).

**How it was verified — real, mixed results, not cherry-picked:**
1. `GET /api/status` on this machine → real logical screen `1680x1050`; real screenshot PNG → `3360x2100` (scale factor 2, confirmed programmatically via `GroundingAgent.toClickSpace`).
2. **Negative result:** `POST /api/pilot/locate` for "the Apple logo menu icon in the top-left corner" (a ~50x25px real target) against a real live screenshot, 3x3 coarse grid (9 real `moondream` queries) → correctly returned `"confidence":"not_found"` — no coarse cell's real response ever mentioned "apple". This is an *honest* failure (no guess offered) rather than the earlier degenerate near-whole-image bounding box from the raw single-pass test.
3. **False-positive result (also reported honestly, not hidden):** `POST /api/pilot/locate` for "the search bar input box on the webpage" returned `"confidence":"high"` with full coarse/fine agreement at a real coordinate — but visually cropping that exact real region of the same screenshot showed it was actually a browser bookmarks/toolbar strip with no search bar at all. `moondream` hallucinated "search bar" consistently across both the coarse and the fine re-ask, so the two-stage agreement check caught disagreement, not hallucination that happened to repeat. This is documented as a real, load-bearing limitation in the README: `"high"` confidence here means *self-consistent*, not *correct*.
4. Did **not** chain a live test through to `POST /api/pilot/click-by-description` on the real desktop in this session: given result (3) above, the risk of a hallucinated-but-self-consistent "high confidence" click landing somewhere unintended on the user's live desktop (open editor, open browser tabs) was judged not worth it for a same-session smoke test. The click-dispatch half of that endpoint reuses the exact same `MouseKeyboardDriver.clickAt` call already verified end-to-end in the previous changelog entry; what's new and what was actually tested here is the coordinate it now receives.

**What is still explicitly NOT claimed:** this is not reliable production-grade grounding. It works for larger, visually distinctive, correctly-identified elements (verified: a real coarse+fine agreement on a real region), fails honestly (returns `not_found`) for small icons that are simply beyond a small local model's ability to see in a coarsely-cropped tile, and can produce confidently-wrong answers when the model hallucinates the same wrong element across both search stages. There was no Set-of-Marks / Accessibility-API element enumeration in this iteration (considered, not implemented then) — see the changelog entry above this one for the real AXUIElement-based cross-check added in a later pass.

## Unreleased — real pixel-coordinate click dispatch

**Gap identified:** the README explicitly stated "Real mouse click-at-coordinates is not implemented" — a capability that real competitors (Anthropic's Claude Computer Use, OpenAI's Computer Use/Operator, bytedance/UI-TARS) all ship as a core primitive.

**What was built:**
- `MouseKeyboardDriver.clickAt(x, y, processName?)` and `doubleClickAt(...)` in `src/mouse_keyboard_driver.ts`, dispatching real macOS mouse clicks at absolute screen coordinates via `osascript -e 'tell application "System Events" to tell process "<name>" to click at {x, y}'`.
- `MouseKeyboardDriver.pressKeyCode(keyCode, modifiers?)` for real keyboard-shortcut dispatch (e.g. Cmd+C) via System Events `key code ... using {command down}`, as opposed to the plain-text `keystroke` used by the pre-existing `typeText`.
- New server endpoints in `server.ts`: `POST /api/pilot/click`, `POST /api/pilot/keycode`, and `actionType: "click" | "double_click"` support on the existing `POST /api/pilot/execute`. All coordinate-bearing actions now pass real `[x, y]` into `SafetyGuard.evaluateAction` instead of the previous hardcoded `[0, 0]`.
- Frontend: clicking directly on the rendered screenshot in the dashboard (`public/app.js`, `setupCanvasClickToRealClick`) now maps the click position back to real absolute screen coordinates (using the actual scale/offset the screenshot image was drawn at) and dispatches a genuine `POST /api/pilot/click` — closing a manual observe → click → re-observe loop that did not exist before.

**How it was verified:**
1. `bun build server.ts --target=bun --outfile=/dev/null` — compiles clean.
2. `node -c public/app.js` — valid syntax.
3. Discovered through direct experimentation that `click at {x,y}` sent to the bare `System Events` application object fails with AppleScript error `-609` ("invalid connection"); `sdef /System/Library/CoreServices/System\ Events.app` confirmed the `at` parameter belongs to the `process` AppleScript class, not `application`. Fixed by targeting a named process (`tell process "Finder" to click at {x,y}`), confirmed with a bare `osascript` call (exit code 0).
4. Started the real server (`bun server.ts`) and exercised the new endpoints with `curl`:
   - `POST /api/pilot/click {"x":300,"y":300,"process":"Finder"}` → `"success":true`, `"output":"Real click dispatched to process \"Finder\" at (300, 300)"`.
   - `POST /api/pilot/click {..., "double":true}` → real double-click, `"success":true`.
   - `POST /api/pilot/keycode {"keyCode":53}` (Escape) → `"success":true`.
   - `POST /api/pilot/execute {"actionType":"click", ...}` → routes through to the same real driver call.
   - Regression check: `POST /api/pilot/execute` with a `sudo rm -rf /` payload still returns `403` — the safety guard was not weakened by this change.
   - Negative-case check: `POST /api/pilot/click` targeting a nonexistent process (`"ThisAppDoesNotExist123"`) returns `"success":false` with an honest empty/error output — not a faked success.

**What is still explicitly NOT claimed:** no model decides *where* to click. The coordinate is supplied by the human (clicking the on-screen screenshot) or by an API caller. There is still no autonomous "observe → decide → click → re-observe" loop running without a human or external driver in it. See the updated README "What this project still does NOT do" sections (English and Italian) for the full, current honesty note.
